# Completion counts as a planning interface

PerfectPower 0.9.7 turns the latest counting and observable-state machinery into a reusable planning interface. A caller supplies resource constraints, quantity domains and an optional compatibility machine. The compiled object answers how many plans are feasible, how many completions remain after a partial decision, where a particular original plan occurs in the population, which plan occupies a requested rank, and what objective can still be achieved. It also samples original plans uniformly by integer rank and retains every maximizing tie. A separate input language represents ordered named action words at an exact positive-cost budget. These two populations share an acyclic completion fold, but retain different mathematical meanings.

The release includes a standard-library Python API, JSON command-line requests, persistent catalogue integration, source examples, independent exhaustive tests, a public benchmark transcription, complete timing and memory ledgers, and a small compiled Lean transport module. It does not claim that a general integer-planning program has been formally verified. The new formal result concerns a literal compatibility quotient and every finite candidate menu supplied to it. The executable counting, routing and original-coordinate operations have targeted independent tests and explicit resource limits.

## The two input meanings

An allocation has a fixed ordered list of variables. Variable j chooses a nonnegative integer quantity x_j from its declared lower and upper bounds and residue class. Its nonnegative resource vector is multiplied by x_j. Each resource total must lie in an inclusive minimum–maximum interval. A rational profit coefficient contributes p_j x_j to the objective. Two original coordinate tuples are different plans even if their resource totals or objectives agree. Their ordering is lexicographic in the declared variable order, with zero-based ranks.

A compatibility machine optionally reads one declared action for each variable's chosen value. A binary decision may map zero to `skip` and one to `take`. A bounded multi-quantity decision can use a larger action map. The mapping is complete on the admissible value domain, and the action is applied once for that variable decision. It is not applied x_j times unless the source model itself encodes that meaning. A disabled transition invalidates the plan, and the final machine state must belong to the supplied accepting set. This supports conditions such as a protected parity or a forbidden combination without identifying different original variable tuples.

An ordered-word problem instead chooses a variable-length sequence of named actions. Each action has a positive integer cost and a rational profit. The word must follow enabled transitions, finish in an accepting state and have the exact requested total cost. Different action orders and different action names remain distinct. Two actions with the same cost and destination still contribute separate branches. Positive costs bound the length and make the completion recurrence acyclic, including when the underlying machine contains cycles. At budget zero there is exactly one empty word when the initial state accepts, and none otherwise.

Allocation counting is not action-permutation counting. The allocation language supplies the order of variable decisions; it does not enumerate every possible acquisition history of the chosen resources. The word language supplies that second interpretation explicitly. This separation is essential for sampling: uniform over original allocations and uniform over original words are two different probability distributions.

## One fold, several useful answers

For a completion state u, let C(u) be its number of feasible leaves, V(u) its greatest remaining objective and T(u) its number of maximizing leaves. An accepting terminal state has C=1, V=0 and T=1. An infeasible state has C=0 and no objective. A branch e to child v contributes C(v) leaves and objective p(e)+V(v). Consequently C(u) is the sum of child counts, V(u) is the maximum of the nonempty branch objectives, and T(u) is the sum of child tie counts exactly on the maximizing branches.

This construction retains ties rather than choosing an arbitrary representative during compilation. Negative and fractional profits are allowed. An empty population has no maximum; it is never assigned objective zero merely because zero is convenient. Conditional optimization includes the objective already committed by the supplied prefix, so its reported value is the best complete-plan value under that prefix. The conditional maximizer count concerns that prefix's own best completions. In contrast, `optimal=True` in rank, selection, sampling and paging refers to the global maximizer population of the whole original model.

Rank selection visits branches in original lexicographic order and subtracts their completion counts until it reaches the branch containing the desired member. Reverse ranking adds counts of preceding branches while following an original plan. For optimal selection the same procedure uses only maximizing branches and their tie counts. These are deterministic inverse operations on complete feasible plans. A partial tuple can be used for completion queries but is refused as a complete ranked plan.

Uniform sampling draws an integer uniformly from 0 through C(root)−1 and selects that member. Sampling global maximizers instead draws from the T(root) ranks. The argument uses the rank bijection, so a quotient state containing several source states does not accidentally receive the weight of only one source representative. The default uses `SystemRandom.randrange`; the request interface also accepts an integer seed for repeatable pseudorandom sampling. Tests exhaust sampling support using a deterministic source of every rank. They test the bijection, not a noisy statistical approximation to uniformity.

## Resource-state compression and compatibility

An allocation DP state records the variable position, remaining minimum needs, remaining upper room and compatibility state. Minimum needs are clipped at zero after a commitment has been met. Upper room is clipped to the greatest possible use of every remaining suffix. Capacity beyond that suffix bound cannot change whether any completion fits, so it can be discarded from the key. Different prefixes can then share one count and objective entry when their remaining decision problem is identical. The variable position stays in the key; profits and action mappings for different variables are never treated as interchangeable.

Acceptance is protected before the finite machine is minimized. The supplied observation at each state is paired with an accepting Boolean. The existing future-equivalence engine then constructs a quotient preserving both observations and action legality, and replays its homomorphism and separation witnesses. This prevents two otherwise identical source states from merging when one accepts and the other does not. Costs and profits are attached to original variable choices or named actions independently of the machine state, so retaining the action labels and acceptance retains those contributions as well.

The 60-slot example uses a four-state machine with two copies of even/odd parity. A skip leaves its state unchanged; a take toggles parity. The accepting states are the two even states. The protected quotient has two states. With capacity at most 30, the exact count of accepted binary allocations is 347,362,666,934,142,456. An independent sum of binomial coefficients for even k≤30 checks that count. The engine selects and samples actual 60-coordinate plans without materializing that population.

`with_resources` creates a new planner with changed resource intervals. The source variable and machine definitions must remain the same for cache reuse. Its copied memo entries are mathematical suffix subproblems keyed by remaining needs and room, so compatible entries remain valid under the new root limits. The original planner is not mutated. In the retained capacity-change example, 991 entries are available for reuse and only 58 new states are compiled after reducing capacity from 30 to 28. Another exact binomial sum checks the new count. The state budget includes reused entries; successive changes cannot silently accumulate unlimited memo storage.

## Routing according to structure

The automatic route is structural rather than a claim to have discovered a universally optimal solver selector. A plain binary allocation with at most twenty variables can use a Gray-code index. Only one decision bit changes between successive candidates, so resource totals and the scaled integer objective update incrementally. Feasible masks are sorted into original lexicographic order. A range tree stores the maximum objective and tie count over each mask interval. Prefixes correspond to contiguous mask intervals, allowing conditional counts and optima without scanning the feasible list.

Repeated small resource capacities can make a completion DP much smaller than the binary candidate space. A conservative capacity-grid estimate identifies such cases and retains the DP route. Other sufficiently small finite products use pruned enumeration with a complete prefix index. Larger supported finite models use memoized completion DP. Caller-selected strategies make these choices inspectable; the interface records the actual strategy, compiled candidates or states, edges and reused entries.

One exact resource budget with positive weights can use the existing rational generating-function population engine. This route supports up to sixteen coordinates within its degree and arithmetic limits. To keep optimization exact without adding an unsupported general unbounded optimizer, it accepts arbitrary objectives for at most two variables, or an objective proportional to the weighted budget for more variables. A two-variable objective is affine along the budget line, so comparing the first and last admissible members gives the maximum; equal endpoint scores mean every member ties. A proportional objective is constant across the whole exact-budget population.

The four-coordinate generating-function example has weights (1,2,1,2), budget 10¹² and objective equal to the resource cost. Its population contains 41,666,666,667,041,666,666,667,750,000,000,001 members. Every member is a maximizer because the objective is fixed by the budget. The route supplies count, original-coordinate rank/selection and prefix completions without enumerating coordinate ranges. An arbitrary nonproportional objective on four unbounded coordinates is refused by this route rather than promoted to a claimed general solution.

## The independent public workload

The numerical workload comes from [J. E. Beasley's OR-Library](https://people.brunel.ac.uk/~mastjjb/jeb/orlib/mknapinfo.html). Its `mknap1` file contains seven historical project-selection test problems attributed to C. C. Petersen's 1967 study. The release retains the downloaded numeric bytes and a lossless planner transcription. Every profit, resource coefficient, upper capacity, variable order and published optimal objective is preserved. In the decimal-profit instance, scaling is exact rational arithmetic, not binary floating approximation.

The first four problems have 6, 10, 15 and 20 binary variables, with ten resource constraints each. Their complete feasible counts are respectively 28, 644, 22,158 and 422,601. Their exact maximum objectives are 3800, 87061/10, 4015 and 6120, matching the published values. Every compared full query bank contains count and optimum plus five selected members, five reverse ranks and five prefix counts. An independently implemented Gray enumeration index agrees with every answer.

The 28-, 39- and 50-variable counting attempts exceed the retained default DP state budget. Their records say `WORK_LIMIT` and contain no complete count. The separate OR-Tools multidimensional branch-and-bound solver finds optimal objectives matching all seven published values. Its candidate assignments are checked directly against the original integer constraints and exact scaled objective, and its optimality status is required. This is a useful optimization baseline, but it does not supply the full counting or sampling interface. The dataset is an independently sourced historical benchmark, not a current customer deployment.

## Timings and memory

The benchmark alternates planner and independent enumeration order across three trials. Cold timings include model construction and the complete five-query bank. Warm timings reuse the compiled object and average twenty repetitions of that bank per trial. The saved ledger contains every measurement, its median, Python version and OR-Tools version. Import time is excluded from solver timings. The OR-Tools column measures model initialization and optimization only, and must not be read as a count-computation comparison.

The measurements do not establish a planner speed advantage over the hand-built binary index. That baseline is narrower: it preindexes the three-coordinate prefix counts used by the bank and omits conditional objective queries, compatibility machines, arbitrary bounded quantity domains and unbounded rational-series populations. The planner supplies those broader operations, but their existence is not evidence that their additional cost is always justified. If only a conventional knapsack optimum is needed, the retained solver baseline is substantially cheaper on these cases.

Fresh subprocesses also measure Linux peak resident memory for each method and case. Those totals include the interpreter, imports, compilation and the queried bank. They are not estimates of the model objects alone. At the 20-variable case the planner process peaks near 90.5 MiB and independent enumeration near 75.9 MiB, while the optimization-only process is near 38.0 MiB. Failed larger counting attempts retain their peak memory as attempted computations, not as completed solutions. Sparse completion states are excellent for repeated small costs, but public multidimensional coefficients can still produce a large state space.

## The compiled mathematical result

`PerfectPower.PlannerTransport` imports only Lean's standard library. Six audited theorems establish a general run-transport identity, the literal four-to-two-state transition identity, transport for every Boolean action word, equality of accepted ordered candidate lists, equality of their counts and equality of arbitrary mapped score lists. The last statement retains the complete score population rather than only one chosen objective value. Filtering the same candidate menu by an additional resource predicate preserves the applicability of the accepted-list equality.

The kernel script checks the example's literal transition table, accepting set and skip/take variable mappings before compiling and auditing the source. All six theorems compile in Lean 4.20.0 and use only standard audited axioms. This establishes the declared protected-machine transport. It does not establish that the Python DP computes the count of every candidate menu, that the routing implementation is correct, or that its sampling code implements a formally verified random source.

The release also emits a source-bound generic SOE proposal for the same colored machine using the existing compiler. That proposal remains explicitly unaccepted unless the optional `--kernel-check` route rebuilds its Mathlib-based foundation and succeeds. Its emitted status is distinct from the completed standard-library transport audit. No Python replay Boolean is promoted to a Lean theorem.

## Running the engine and interpreting limits

From an extracted checkout, run `python python/run_planning.py` to reproduce the examples and deterministic receipts. Run `python -m perfectpower plan examples/planning/petersen_6.json` after installation to execute a JSON request. That file contains a source specification and a list of method calls; the source is compiled once for the list. Catalogue kind `completion_planner` retains the definition and compiled object for subsequent service calls. Exact large counts remain Python integers; external JSON clients must preserve their integer digits rather than parse them through a floating number type.

Run `make planning-test` for independent allocation and word enumeration, residue and capacity intervals, negative fractional profits, optimal ties, sampling support, rank inverses, source acceptance, cache reuse and installed interface behavior. Run `make planning-kernel` with Lean 4.20.0 to reproduce the six-theorem audit. Install `.[planning-benchmark]` and run `make planning-benchmark` for the public comparisons and fresh-process memory measurements. The core planner has no external runtime dependency; the pinned OR-Tools package is only needed for that baseline.

General finite allocation folds allow at most 64 variables, sixteen resources and 256 admissible values per variable. Default completion work limits are 200,000 states and two million edges, with configurable maxima of one million and four million. The binary route is separately bounded by twenty decision bits. Word budgets are at most 256, with positive action costs from one through sixteen. Rational-series limits remain those of the existing generating-function engine. A refused model or an exhausted budget is an unresolved computation, never an empty population or a complete infeasibility result. The next application should measure these routes on its actual models and queries, retaining the narrow fast alternative whenever it suffices.
